## 一、核心重写

### Q30 / Q53 元素定位优先级

**答：** 我的优先级是 **id → CSS Selector → XPath**，`name` / `link_text` 作为补充。

理由是分两层看：

- **id** 走浏览器原生 `getElementById`，最快也最稳定，能用就用；
- **CSS** 走原生 `querySelector`，同样是引擎原生实现，语法简洁、可读性好，执行效率高于 XPath；
- **XPath** 由 Selenium 的 XPath 引擎解析，功能最强但最慢，我只在这三种情况用它：**按文本定位**、**轴定位**（从子元素反查父元素、兄弟节点）、以及 CSS 选择器表达不出来的复杂层级。

补充一个容易踩的点：CSS 里的 `:contains()` 不是标准 CSS，Selenium 不支持，所以“按按钮文字点登录”只能用 XPath。

```python
dr.find_element(By.ID, "username")                              # 1. id：最快最稳
dr.find_element(By.CSS_SELECTOR, "input.el-input__inner")        # 2. CSS：类/属性/组合
dr.find_element(By.XPATH, '//span[text()="登录"]')                # 3. XPath：按文本
dr.find_element(By.XPATH, '//label[text()="用户名"]/following-sibling::div//input')  # 轴定位反查
dr.find_element(By.NAME, "username")                             # 补充：name
dr.find_element(By.LINK_TEXT, "忘记密码")                          # 补充：link_text
```

**接 RuoYi 项目**：RuoYi-Vue 前端是 Element UI，组件 class 语义化（`.el-input__inner`、`.el-button--primary`），用 CSS 定位很顺；但登录按钮这类只有文字、没有稳定 class 的元素，我就用 XPath 文本定位。

**稳定性口径（Q53 同用）**：一是 **选用稳定的定位方式**——优先 id，其次语义化 CSS，避免绝对路径和动态 id；二是 **合理使用等待**——用显式等待代替 sleep，等元素出现而不是死等固定时间。另外用例之间不互相依赖、测试数据可重复、失败自动重试并截图留痕。

> [!tip] 口径提醒
> 也见过 `id > XPath > CSS` 的说法。两种在业界都常见，**关键是讲清选择理由**，别在同一个回答里前后矛盾。

### Q61 QPS 和 TPS 的区别

**答：** QPS 是 **每秒请求数**，统计服务器收到的请求量；TPS 是 **每秒事务数**，统计完整业务事务的数量。一个事务通常包含多次请求——比如下单这个事务，可能包含查库存、锁库存、生成订单、核销优惠券 4 次请求，那么 1 个 TPS 对应 4 个 QPS。

**两者没有固定换算比例**，完全取决于业务链路长短：单接口的增删改查，QPS 和 TPS 基本 1:1；复杂下单链路常见 5:1 甚至 10:1——10:1 是业界常用的经验参考值，但它是估出来的，不是公式。

在 JMeter 里我是这么区分的：**事务控制器** 把多个 sampler 打包成一个事务来统计 TPS；单个 sampler 的吞吐量就是 QPS。

### Q62 性能指标

**答：** 我关注四个维度，量化标准是这样：

| 维度 | 标准 | 说明 |
|---|---|---|
| 响应时间 | P90 ≤ 500ms，P99 ≤ 1s | 平均值意义不大，看 **分位数** |
| 事务成功率 | 核心接口（下单/支付）≥ 99.9%，普通接口 ≥ 99.5% | 即错误率 ≤ 0.1% / 0.5% |
| 服务器资源 | CPU ≤ **70%**，内存 ≤ 80% | 另看磁盘 IO wait、网络丢包 |
| Java 应用专项 | Full GC 频率与耗时 | RuoYi 这类 Spring Boot 应用必看 |
| 拐点并发 | TPS 走平、响应时间陡增处 | 即当前架构容量上限 |

**为什么 CPU 卡 70% 而不是 90%**：到 90% 已经在过载边缘，请求开始排队、响应时间急剧恶化，线上还要留 30% 余量应对突发流量。留到 90% 才报警等于没报警。

JMeter 侧看 **聚合报告**（Average / 90% Line / Error% / Throughput），服务器资源靠 **PerfMon 插件** 采集。

> [!tip] 口径备选
> 也见过 CPU 不高于 90%、核心接口成功率 99.5% 的口径（部分公司/课程采用）。我按更严的一档答，被问“你们到底按多少”时能解释清楚取严的理由。

### Q64 阶梯加压

**答：** Ramp-up 和阶梯加压是两个不同的机制，我分开说：

- **Ramp-up**：普通线程组的“启动时间”，让 N 个线程在 X 秒内 **线性** 启动，作用是避免冷启动瞬间打满，它不是阶梯；
- **阶梯加压**：并发数 **分档递增并保持**，比如 50 → 100 → 150 → 200，每档持续 3 分钟，观察每档的 TPS 与响应时间曲线。

JMeter 原生线程组做不了阶梯，需要装 **jpgc 插件** 的 Stepping Thread Group，字段是这几个：

- `This group will start` — 起始线程数
- `First, wait for` — 起始等待
- `Then start` — 首批启动线程数
- `Next, add __ threads every __ seconds, using ramp-up __ seconds` — 每档递增 N 个、间隔 Y 秒、爬坡 R 秒
- `Then hold load for` — 每档持续时长
- `Finally, stop __ threads every __ seconds` — 结束时递减

**停止加压的信号（拐点）**：并发继续涨，但 TPS 不再上升甚至下降、响应时间明显陡增——拐点对应的并发数就是当前架构的处理能力。

### Q23 / Q55 自动化框架分层

**答：** 我们框架是 **代码三层 + 一个数据目录**：

> “代码分三层——`core/` 基础层、`pages/` 页面层、`test/` 用例层，另外有一个 `test_data/` 数据目录，合起来是四层结构。”

| 层 | 内容 |
|---|---|
| `core/` | `driver_manager.py`（驱动/浏览器实例/等待器）+ `base_page.py`（open、find_element 内置显式等待、input_text、click、screenshot） |
| `pages/` | 一个页面一个类，定位器元组 + 页面操作方法 |
| `test/` | 只写步骤和断言，配 `conftest.py` 的 fixture |
| `test_data/` | csv / yaml 测试数据，pandas / yaml 读取 |

入口 `main.py`，配置 `pyproject.toml`（`addopts` 出 HTML 报告、timeout），报告落 `reports/`。

分层收益：元素变了只改 `pages/` 一处，数据变了只改 `test_data/`，用例不动。

> 三层还是四层，主动把口径交代清楚，别前后打架。

### Q47 私有属性与 `@property`

```python
class Ren:
    def __init__(self, mz, nl):
        self.name = mz        # 公有属性，外部可直接读写
        self.__age = nl       # 私有属性，名字被修饰为 _Ren__age

    @property                # 读：把方法伪装成属性
    def age(self):
        return self.__age    # 返回真实值（getter 里可以加工，但业务语义上应返回真实值）

    @age.setter              # 写：这里才能加校验
    def age(self, nl2):
        if not 0 <= nl2 <= 150:
            raise ValueError("年龄不合法")
        self.__age = nl2

r1 = Ren('张三', 50)
print(r1.name, r1.age)   # 张三 50
r1.age = 51              # 触发 setter
print(r1.age)            # 51
```

**要点**：私有属性外部和子类都访问不到（子类里的 `self.__age` 会被修饰成 `_子类名__age`，不是同一个）；严格说 Python 的“私有”是 **约定而非强制**，通过 `_Ren__age` 仍能强行访问。`@property` 的真实价值在于 setter 里能加校验——直接暴露公有属性是做不到的；`@x.setter` 必须写在 `@property` 之后，不能单独用。

> [!tip] 追问准备
> 如果被问“getter 里能不能返回别的值”——能，`getter` 本质是方法，可以返回加工后的结果；但 **作答时按业务语义返回真实值** 更稳。

### Q8 增删改语句与 DDL / DML

**答：** `UPDATE` 是 DML，改表里的数据，可回滚；`ALTER` 是 DDL，改表结构（加字段、改类型），**MySQL 里 DDL 会隐式提交事务**，执行即生效且不能回滚。线上大表 `ALTER` 有风险：MySQL 5.6 以前多数 DDL 会锁表，8.0 起支持 `INSTANT` / `INPLACE` 可以减小影响，但仍然要走变更窗口评估。

删除有三个层次，容易混：

| 语句 | 类型 | 特点 |
|---|---|---|
| `DELETE FROM t WHERE ...` | DML | 逐行删、可带条件、可回滚、不释放空间 |
| `TRUNCATE TABLE t` | DDL | 清空整表、不可回滚、重置自增 |
| `DROP TABLE t` | DDL | 删表本身 |

测试里清数据我只用 `DELETE` + WHERE 条件，不用 `TRUNCATE`——条件写错就是整表没了。

### Q11 索引

**答：** 索引用来提高查询效率，类似书的目录，避免全表扫描；复合索引遵循 **最左前缀原则**。但实际导致“查询慢”的更多是索引失效：

- 对字段做函数运算（`WHERE DATE(create_time) = ...`）
- 隐式类型转换（字符串字段传了数字）
- `LIKE '%xxx'` 前缀通配
- `OR` 连接了非索引列
- 违反最左前缀
- 优化器判断全表更快（数据量小或区分度低）

另外两个概念：**回表**——二级索引查到主键后还要回主键树取整行；**覆盖索引**——查询字段全在索引里，不用回表，`EXPLAIN` 的 Extra 显示 `Using index`。

测试视角：我用 `EXPLAIN` 看 `type`，性能从好到差是 `system > const > eq_ref > ref > range > index > ALL`，一般要求至少到 `range`，理想是 `ref` / `eq_ref` / `const`，看到 `index` 或 `ALL` 就要考虑优化；再看 `rows`（扫描行数）、有没有 `Using filesort` / `Using temporary`。

### Q37 事务与回滚

**答：** 事务把一组 SQL 作为不可分割的执行单元，遵循 **ACID**（原子性、一致性、隔离性、持久性）：要么全部成功（COMMIT），要么全部失败回滚（ROLLBACK）。

ACID 之外还有隔离级别，这是必追问点：

| 隔离级别 | 解决的问题 |
|---|---|
| 读未提交 | —（脏读、不可重复读、幻读均存在） |
| 读已提交（RC） | 脏读 |
| 可重复读（RR） | 脏读、不可重复读 |
| 串行化 | 脏读、不可重复读、幻读 |

**MySQL InnoDB 默认 RR，Oracle 默认 RC。**

测试相关的坑：RR 下同一事务内两次查同一条记录结果一致（快照读），所以我核对数据一定在事务外查，否则看到的是旧快照，会误判成 bug 没修复。

再深一层：RR 下如果出现 **当前读**（`UPDATE` / `SELECT ... FOR UPDATE`），会读到其他事务已提交的修改，仍可能出现幻读式不一致，InnoDB 靠 **next-key lock（行锁 + 间隙锁）** 兜底。

### Q1 Get / Post 区别

**答：** 参数位置不同——Get 拼在 URL 后面（Query String），Post 放在请求体 Body 中。

长度方面，HTTP 协议本身 **没有规定 URL 长度**，限制来自浏览器和服务器：IE 早期 2083 字符；服务端 Apache `LimitRequestLine` 默认 8190 字节、Nginx 默认 8K；Chrome 自身能支持到 MB 级，但实际以服务端为准，工程上一般按 **2KB 以内** 控制。

另外：Get 可以被缓存、可收藏为书签，Post 不可缓存；**Post 也不安全**——只是参数不在 URL、地址栏和浏览器历史里明文显示，抓包一样看得见，敏感数据必须走 HTTPS。

测试角度：Get 传参在 Postman 里写在 Params 区，Post 在 Body 区（x-www-form-urlencoded / form-data / raw-JSON），前置脚本里 Get 取 `pm.request.url.query`、Post 取 `pm.request.body.urlencoded`。

### Q31 元素定位失败的原因

**答：** 常见八类：

1. **动态 ID**——id 每次刷新都变，改用相对 XPath（按文本/属性）；
2. **元素未加载完成**——加显式等待；
3. **页面刷新 / 弹窗**——重新定位或先处理弹窗；
4. **元素被遮挡或不在可视区**——先滚动到元素，或等遮罩消失；
5. **iframe 嵌套**——先 `switch_to.frame()` 切进去，操作完再切回来。RuoYi-Vue 绝大多数页面是 `router-view` 渲染，不用切 iframe，只有“外部/内部链接”型菜单（监控页、Swagger）才需要；
6. **定位不唯一**——`find_element` 只返回第一个匹配项，多个元素匹配同一表达式时拿到的不一定是你要的，用 `find_elements` 确认数量；
7. **Shadow DOM**——元素在 shadow root 里，普通 XPath 穿透不了，得用 JS 取 `shadowRoot` 再查。

解决思路总结：先确认定位器唯一且稳定，再确认等待时机，最后确认是否在 iframe / 新窗口里。

### Q32 三种等待机制

**答：** 一是 **硬等待** `time.sleep(5)`——强制等固定时间，死等，只在调试时用；二是 **隐式等待** `dr.implicitly_wait(10)`——全局设置，找元素时最多等 10 秒；三是 **显式等待** `WebDriverWait`——针对单个元素设定条件和超时时间，最灵活：

```python
wait_10 = WebDriverWait(dr, 10)
el = wait_10.until(EC.presence_of_element_located((By.ID, "username")))
```

还有一个坑：**隐式等待和显式等待不要混用**。隐式等待作用于所有 `find_element`，显式等待是轮询，两者叠加时实际超时会变成“显式超时 + 隐式超时”，排查起来非常痛苦。我的做法是 **只用显式等待，隐式设 0**。

### Q67 Java vs Python

**答：** 三点主要差别：一是 Java 先编译成字节码再由 JVM 执行（含 JIT 编译），Python 是解释执行；二是 Java 是 **强类型、静态类型**，Python 是 **动态类型**；三是适用场景——Java 多用于大型后端服务，Python 上手快、库丰富，适合测试脚本和自动化。

还有一点——Python 有 **GIL（全局解释器锁）**，同一时刻只有一个线程执行字节码，CPU 密集场景多线程跑不满多核，得上多进程；IO 密集（发 HTTP 请求、等元素出现）则不受影响。Java 没有这个限制，是真并行，这也是 JMeter 这类压测工具用 Java 写的原因之一。

### Q15 ECMobile 真实接口

```json
接口一：用户登录POST http: //localhost/ecmobile/?url=/user/login Content-Type: application/x-www-form-urlencoded表单字段：json={
  "name": "ecshop",
  "password": "ecshop"
}响应：data.session里返回uid+sid，后续接口都要带上
```

不同情况：账号密码正确 → 返回 uid/sid；密码错误 → status 返回错误码；json 参数缺失或格式错 → 报错；未带 session → 后续接口鉴权失败。

```json
接口二：商品搜索POST http: //localhost/ecmobile/?url=/search表单字段：json={
  "session": {
    "uid": "${uid}",
    "sid": "${sid}"
  },
  "filter": {
    "keywords": "P806",
    "sort_by": "price_asc"
  },
  "pagination": {
    "page": 1,
    "count": 10
  }
}
```

不同情况：正常返回商品列表；关键词为空 → 返回全部或报错；分页超界 → 空列表；session 失效 → 鉴权失败；排序字段非法 → 默认排序。

**两套认证机制都讲，是加分项**：

> ECMobile 这套是 `uid + sid` 放在 json 的 session 字段里传递，不是标准 token；RuoYi-Vue 那边是 `POST /login` 拿 JWT，前端存进 cookie（`Admin-Token`），后续请求走 `Authorization: Bearer <token>`。两种机制不一样但思路一样——登录后提取凭证，后续请求带上。
> `[需确认：RuoYi 侧是否真在接口层实操过，还是仅了解机制]`

### Q10 多表联查

```sql
SELECT o.order_sn, o.order_amount, og.goods_name, og.goods_number
FROM ecs_order_info o
JOIN ecs_order_goods og ON o.order_id = og.order_id
WHERE o.user_id = 1001;
```

RuoYi 侧用 `sys_user` 左连 `sys_dept` 核对用户归属部门，用 LEFT JOIN 是为了让“没分配部门的用户”也出现在结果里。

### Q34 兼容性测试

**答：** 分两条线：

**浏览器**——主要覆盖 Chrome 和 Edge（都是 Chromium 内核），另外验 Firefox，重点看 CSS 布局错位和 JS 报错。我会用 F12 的 Device Toolbar 快速切分辨率，Safari 用云测平台补。

**我实际做过的专项**：AEAI CRM 二期我负责登录、潜在客户、订单管理三个模块，用例是按 **界面文字**（缩放 / 二义性 / 粗细）、**图片缩放**、**排版**、**网络**（断网 / 限速 / 刷新）四个维度拆的，最后按禅道 CSV 格式分批导入。这属于兼容 + 易用性的专项验证，不是单纯的功能用例。`[需确认：导入禅道的用例数量级，量化比形容词管用]`

### Q35 有成就感的事

按 TAR 讲：

> **T（任务）**：接手 ECMobile 商城 App 的接口测试，主档 40+ 个接口。
> **A（行动）**：按文档把接口录进 Postman 后，批量请求全部返回 404。我没有直接提缺陷，而是先用 Fiddler 抓前端真实发出的请求报文，跟文档里的路径逐段对比，定位到是 Base URL 少了一层 `index.php`、伪静态没配，属于环境配置问题而不是接口逻辑问题。确认后我推动开发补齐 rewrite 规则，并把正确的 Base URL 约定（`ecmobile/?url=<path>`）同步回接口文档。
> **R（结果）**：整批接口一次打通，后面 16 个核心接口的用例和自动化才跑得起来。这件事给我留下一个习惯——**接口报错先分清楚是环境/路径问题还是逻辑问题，别急着提单**。
>
> [!warning] 背诵前必须核实
> 上面“404 根因是缺 `index.php`”目前仍是推断，笔记里的记录是“排查中”。**最终根因以你确认过的结论为准**——编造的技术细节在追问环节最容易崩。

## 五、追问预设（分层递进）

> [!tip] 用法
> 答完主问题才是开始。下面 6 条是最高频的追问链，**每条都要能答到第三层**。

| 主问题 | 第一层 | 第二层 | 第三层 |
|---|---|---|---|
| 索引的用途 | 为什么加了索引还是慢？ | `EXPLAIN` 怎么读？`type` 好坏顺序？ | 覆盖索引 / 回表？大表加索引要注意什么（Online DDL、锁表）？ |
| 事务与回滚 | ACID 指什么？ | 隔离级别有哪些？MySQL 默认？ | RR 下为什么还会有幻读？间隙锁是什么？ |
| 性能指标 | 关注哪些指标？ | 指标谁定的？怎么保证合理？ | 不达标从哪几层排查（网络 → 应用 → 数据库 → 依赖）？ |
| 阶梯加压 | 线程组怎么配？ | Ramp-up 和阶梯有什么区别？ | 拐点怎么判？JMeter 自身会不会成为瓶颈（要不要分布式压测）？ |
| 测试数据管理 | 数据怎么管？ | 为什么用文件不用数据库？ | 用例间数据冲突怎么办？跑完怎么清理？ |
| 接口举例 | 这个接口做什么？ | 用例怎么设计（等价类/边界值/异常）？ | 断言怎么写？落库怎么验？上下游依赖怎么串？ |
