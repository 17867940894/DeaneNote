## 一、总体判断

这份文档的**技术判断力在线**——能自己揪出原稿里 CPU 90%、QPS:TPS 换算、`@property` 返回值这类问题，说明底层是扎实的。真正的风险不在技术，在**三处结构性错位**：

| 结构问题 | 说明 | 影响 |
|---|---|---|
| **文档身份分裂** | 同一段里既有候选人口吻（"我的优先级是…"），又有审稿人旁白（"原稿写反了""自杀""画蛇添足"） | 照着念会把"原稿写反了"这种话带进面试，当场社死 |
| **定性过重** | 把"与课程口径不一致"标成"致命/杜撰" | 逼你背一套和课程、和课堂笔记相反的答案，被追问时两头不靠 |
| **只有答案、没有追问链** | 全文是平铺的一问一答 | 真实面试 70% 的信息量在追问里，答完主问题才是开始 |

## 四、题目设置与追问逻辑审查（原稿 69 题维度）

### 4.1 难度梯度：基本合理，中段偏平

- **梯度现状**：P1（概念与操作）→ P2（原理与方案）→ 冷门/高阶 → 测开级 → 性能，梯度是有的；
- **问题**：P2 中段（数据库 / 接口 / Python 三块）**并列平铺，没有爬坡**，候选人背完就到顶，区分度不足；
- **建议**：在这三块各加一层"为什么"（为什么这么设计、不这么做会怎样），形成"是什么 → 怎么做 → 为什么 → 出问题怎么排查"的四段爬坡。

### 4.2 追问链缺失（最大短板）

现有文档是**平铺问答**，没有为高频题预设追问。以下是真实面试里最常被追的 6 条链，已在修订版 §6 补齐：

| 主问题 | 第一层追问 | 第二层追问 | 第三层追问 |
|---|---|---|---|
| 索引的用途 | 为什么加了索引还是慢？ | `EXPLAIN` 怎么读？`type` 好坏顺序？ | 覆盖索引 / 回表？大表加索引要注意什么？ |
| 事务与回滚 | ACID 指什么？ | 隔离级别有哪些？MySQL 默认？ | RR 下为什么还会有幻读？间隙锁是什么？ |
| 性能指标 | 关注哪些指标？ | 指标谁定的？怎么保证合理？ | 指标不达标从哪几层排查？ |
| 阶梯加压 | 线程组怎么配？ | Ramp-up 和阶梯有什么区别？ | 拐点怎么判？JMeter 自身会不会成为瓶颈？ |
| 测试数据管理 | 数据怎么管？ | 为什么用文件不用数据库？ | 用例间数据冲突怎么办？跑完怎么清理？ |
| 接口举例 | 这个接口做什么？ | 用例怎么设计？ | 断言怎么写？落库怎么验？上下游依赖怎么处理？ |

### 4.3 遗漏考点（原稿 69 题未覆盖，但 1~3 年岗高频）

| 遗漏点 | 常见问法 | 一句话答法要点 |
|---|---|---|
| **幂等性与防重** | 重复点击提交、网络重传导致重复下单怎么测？ | 前端置灰防抖 + 后端唯一 token / 唯一流水号校验，Postman 并发两次验证 |
| **HTTPS 抓包** | Fiddler 抓 HTTPS 为什么要装证书？ | 中间人代理，需信任根证书；Android 7+ 还需信任用户证书才能抓 App 包 |
| **慢查询与锁** | 页面很慢你怎么定位？ | 慢查询日志 → `EXPLAIN` → 看锁等待（`SHOW PROCESSLIST` / `innodb_trx`）→ 区分行锁/表锁/死锁 |
| **契约 / Schema 校验** | 接口字段被悄悄改了你怎么办？ | 响应结构（JSON Schema）校验进断言，比只断 `code` 更早发现字段增删 |
| **CI 质量门禁** | 自动化在流水线里怎么卡质量？ | 构建后触发 → 看退出码阻断 → 报告归档 → 失败通知到人 |
| **失败重试与并发执行** | 用例偶发失败怎么处理？ | 先区分环境波动与真缺陷；重试机制 + `pytest-xdist` 并发提速，但重试不掩盖 flaky 根因 |
| **日志链路排查** | 线上问题你怎么查？ | `tail -f` + `grep` 关键字 → 按 traceId / 订单号串链路 → 结合数据库落库比对 |
