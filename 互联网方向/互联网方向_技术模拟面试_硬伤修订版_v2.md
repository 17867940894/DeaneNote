### Q30 / Q53 元素定位优先级

> [!note] 内部提示
> 原稿 `id > XPath > CSS` 与课堂笔记一致，这里给的是更主流的口径。面试时两种都能站住，**关键是讲清理由**，别前后矛盾。

**答：** 我的优先级是 **id → CSS Selector → XPath**，`name` / `link_text` 作为补充。

理由是分两层看：

- **id** 走浏览器原生 `getElementById`，最快也最稳定，能用就用；
- **CSS** 走原生 `querySelector`，同样是引擎原生实现，语法简洁、可读性好，执行效率高于 XPath；
- **XPath** 由 Selenium 的 XPath 引擎解析，功能最强但最慢，我只在这三种情况用它：**按文本定位**、**轴定位**（从子元素反查父元素、兄弟节点）、以及 CSS 选择器表达不出来的复杂层级。

补充一个容易踩的点：CSS 里的 `:contains()` 不是标准 CSS，Selenium 不支持，所以“按按钮文字点登录”只能用 XPath。〔已修订：统一中文引号，原文为英文直引号〕

```python
dr.find_element(By.ID, "username")                              # 1. id：最快最稳
dr.find_element(By.CSS_SELECTOR, "input.el-input__inner")        # 2. CSS：类/属性/组合
dr.find_element(By.XPATH, '//span[text()="登录"]')                # 3. XPath：按文本
dr.find_element(By.XPATH, '//label[text()="用户名"]/following-sibling::div//input')  # 轴定位反查
dr.find_element(By.NAME, "username")                             # 补充：name
dr.find_element(By.LINK_TEXT, "忘记密码")                          # 补充：link_text
```

〔已修订：正文提到了 `name` / `link_text`，原代码只演示三种，补齐示例，避免“说到没做到”〕

**接 RuoYi 项目**：RuoYi-Vue 前端是 Element UI，组件 class 语义化（`.el-input__inner`、`.el-button--primary`），用 CSS 定位很顺；但登录按钮这类只有文字、没有稳定 class 的元素，我就用 XPath 文本定位。

> Q53「如何保证脚本稳定性」用同一套口径，别再冒出“其次用 XPath”。

### Q61 QPS 和 TPS 的区别

**答：** QPS 是**每秒请求数**，统计服务器收到的请求量；TPS 是**每秒事务数**，统计完整业务事务的数量。一个事务通常包含多次请求——比如下单这个事务，可能包含查库存、锁库存、生成订单、核销优惠券 4 次请求，那么 1 个 TPS 对应 4 个 QPS。

**两者没有固定换算比例**，完全取决于业务链路长短：单接口的增删改查，QPS 和 TPS 基本 1:1；复杂下单链路常见 5:1 甚至 10:1。〔已修订：原写“所谓 10:1 没有依据/杜撰”，改为“经验值而非公式”——课程文档里 10:1 是经验参考口径，直接否定会与面试官可能的认知冲突，也会被追问〕

在 JMeter 里我是这么区分的：**事务控制器**把多个 sampler 打包成一个事务来统计 TPS；单个 sampler 的吞吐量就是 QPS。

### Q62 性能指标（CPU 阈值与分位数）

**答：** 我关注四个维度，量化标准是这样：

| 维度 | 标准 | 说明 |
|---|---|---|
| 响应时间 | P90 ≤ 500ms，P99 ≤ 1s | 平均值意义不大，看**分位数** |
| 事务成功率 | 核心接口（下单/支付）≥ 99.9%，普通接口 ≥ 99.5% | 即错误率 ≤ 0.1% / 0.5% |
| 服务器资源 | CPU ≤ **70%**，内存 ≤ 80% | 另看磁盘 IO wait、网络丢包 |
| Java 应用专项 | Full GC 频率与耗时 | RuoYi 这类 Spring Boot 应用必看 |
| 拐点并发 | TPS 走平、响应时间陡增处 | 即当前架构容量上限 |

**为什么 CPU 卡 70% 而不是 90%**：到 90% 已经在过载边缘，请求开始排队、响应时间急剧恶化，线上还要留 30% 余量应对突发流量。留到 90% 才报警等于没报警。

JMeter 侧看**聚合报告**（Average / 90% Line / Error% / Throughput），服务器资源靠 **PerfMon 插件**采集。

> [!note] 口径提示
> 课程文档给的是“核心接口 ≥99.5%~99.7% / CPU 不高于 90%（或 70%）”。这里取更严的一档，**答严不答松**——但要知道两个数都出现过，被追问“你们到底按多少”时能解释清楚。

### Q64 阶梯加压（Ramp-up ≠ 阶梯）

**答：** 这两个是不同的机制，我分开说：

- **Ramp-up**：普通线程组的“启动时间”，让 N 个线程在 X 秒内**线性**启动，作用是避免冷启动瞬间打满，它不是阶梯；
- **阶梯加压**：并发数**分档递增并保持**，比如 50 → 100 → 150 → 200，每档持续 3 分钟，观察每档的 TPS 与响应时间曲线。

JMeter 原生线程组做不了阶梯，需要装 **jpgc 插件**的 Stepping Thread Group。它的字段是这样：〔已修订：原字段名 `Then add X threads every Y seconds` / `hold load for Z seconds` 是意译，JMeter 里实际标签如下，按真实标签说更可信〕

- `This group will start` — 起始线程数
- `First, wait for` — 起始等待
- `Then start` — 首批启动线程数
- `Next, add __ threads every __ seconds, using ramp-up __ seconds` — 每档递增 N 个、间隔 Y 秒、爬坡 R 秒
- `Then hold load for` — 每档持续时长
- `Finally, stop __ threads every __ seconds` — 结束时递减

**停止加压的信号（拐点）**：并发继续涨，但 TPS 不再上升甚至下降、响应时间明显陡增——拐点对应的并发数就是当前架构的处理能力。

### Q47 `@property` 示例修正

原稿 `@property def age()` 写死 `return 18`，没返回真实年龄，作为面试答案会显得答非所问。正确版：

```python
class Ren:
    def __init__(self, mz, nl):
        self.name = mz        # 公有属性，外部可直接读写
        self.__age = nl       # 私有属性，名字被修饰为 _Ren__age

    @property                # 读：把方法伪装成属性
    def age(self):
        return self.__age    # 原稿写死 return 18，不符合预期语义

    @age.setter              # 写：这里才能加校验
    def age(self, nl2):
        if not 0 <= nl2 <= 150:
            raise ValueError("年龄不合法")
        self.__age = nl2

r1 = Ren('张三', 50)
print(r1.name, r1.age)   # 张三 50
r1.age = 51              # 触发 setter
print(r1.age)            # 51
```

**要点**：私有属性外部和子类都访问不到（子类里的 `self.__age` 会被修饰成 `_子类名__age`，不是同一个）；严格说 Python 的“私有”是**约定而非强制**，通过 `_Ren__age` 仍能强行访问。〔已修订：补这一句，避免被追问时答死〕`@property` 的真实价值在于 setter 里能加校验——直接暴露公有属性是做不到的；`@x.setter` 必须写在 `@property` 之后，不能单独用。

> [!note] 内部提示
> 课堂笔记里 `return 18` 是教学演示（演示 getter 可以返回加工后的值），不是笔误；但**面试作答要返回真实值**。

### Q8 增删改语句与 DDL / DML

**补充答：** `UPDATE` 是 DML，改表里的数据，可回滚；`ALTER` 是 DDL，改表结构（加字段、改类型），**MySQL 里 DDL 会隐式提交事务**，执行即生效且不能回滚。线上大表 `ALTER` 有风险：MySQL 5.6 以前多数 DDL 会锁表，8.0 起支持 `INSTANT` / `INPLACE` 可以减小影响，但仍然要走变更窗口评估。〔已修订：原写“会锁表”过于绝对，补版本差异与 Online DDL〕

删除有三个层次，容易混：

| 语句 | 类型 | 特点 |
|---|---|---|
| `DELETE FROM t WHERE ...` | DML | 逐行删、可带条件、可回滚、不释放空间 |
| `TRUNCATE TABLE t` | DDL | 清空整表、不可回滚、重置自增 |
| `DROP TABLE t` | DDL | 删表本身 |

测试里清数据我只用 `DELETE` + WHERE 条件，不用 `TRUNCATE`——条件写错就是整表没了。

### Q11 索引（补失效场景与判读）

**补充答：** 除了最左前缀，实际导致“查询慢”的更多是索引失效：

- 对字段做函数运算（`WHERE DATE(create_time) = ...`）
- 隐式类型转换（字符串字段传了数字）
- `LIKE '%xxx'` 前缀通配
- `OR` 连接了非索引列
- 违反最左前缀
- 优化器判断全表更快（数据量小或区分度低）

另外两个概念：**回表**——二级索引查到主键后还要回主键树取整行；**覆盖索引**——查询字段全在索引里，不用回表，`EXPLAIN` 的 Extra 显示 `Using index`。

测试视角：我用 `EXPLAIN` 看 `type`，性能从好到差是 `system > const > eq_ref > ref > range > index > ALL`，一般要求至少到 `range`，理想是 `ref` / `eq_ref` / `const`，看到 `index` 或 `ALL` 就要考虑优化；再看 `rows`（扫描行数）、以及有没有 `Using filesort` / `Using temporary`。〔已修订：补全 type 排序与 `eq_ref`，原文漏项〕

### Q37 事务与回滚（补隔离级别）

**补充答：** ACID 之外还有隔离级别，这是必追问点：

| 隔离级别 | 解决的问题 |
|---|---|
| 读未提交 | —（脏读、不可重复读、幻读均存在）〔已修订：原写“（有脏读）”，不完整〕 |
| 读已提交（RC） | 脏读 |
| 可重复读（RR） | 脏读、不可重复读 |
| 串行化 | 脏读、不可重复读、幻读 |

**MySQL InnoDB 默认 RR，Oracle 默认 RC。**

测试相关的坑：RR 下同一事务内两次查同一条记录结果一致（快照读），所以我核对数据一定在事务外查，否则看到的是旧快照，会误判成 bug 没修复。

再深一层：RR 下如果出现**当前读**（`UPDATE` / `SELECT ... FOR UPDATE`），会读到其他事务已提交的修改，仍可能出现幻读式不一致，InnoDB 靠 **next-key lock（行锁 + 间隙锁）** 兜底。〔已修订：补当前读与间隙锁，这是这道题的第三层追问点〕

### Q1 Get / Post 区别（长度说法要严谨）

**修订点：** HTTP 协议本身**没有规定 URL 长度**，限制来自浏览器和服务器：IE 早期 2083 字符；服务端 Apache `LimitRequestLine` 默认 8190 字节、Nginx 默认 8K；Chrome 自身能支持到 MB 级，但实际以服务端为准，工程上一般按 **2KB 以内**控制。〔已修订：原写“Chrome / Apache 一般 8KB 左右”，把浏览器限制与服务端限制混为一谈〕

另一句要补：**Post 也不安全**——只是参数不在 URL、地址栏和浏览器历史里明文显示，抓包一样看得见，敏感数据必须走 HTTPS。

在原稿五类基础上补：

- **第六类（原稿已提 iframe）**——补充：RuoYi-Vue 绝大多数页面是 `router-view` 渲染，**不用切 iframe**；只有菜单类型是“外部/内部链接”（监控页、Swagger）时才需要 `switch_to.frame()` 切进去。
- **第七类：定位不唯一**——`find_element` 只返回第一个匹配项，页面上有多个元素匹配同一表达式时，拿到的不一定是你要的。用 `find_elements` 确认数量。
- **第八类：Shadow DOM**——元素在 shadow root 里，普通 XPath 穿透不了，得用 JS 取 `shadowRoot` 再查。

---

### Q32 三种等待（补混用陷阱）

**补充答：** 还有一个坑——**隐式等待和显式等待不要混用**。隐式等待作用于所有 `find_element`，显式等待是 `WebDriverWait` 轮询，两者叠加时实际超时会变成“显式超时 + 隐式超时”，排查起来非常痛苦。我的做法是**只用显式等待，隐式设 0**。

---

### Q67 Java vs Python（补 GIL）

**补充答：** 还有一点——Python 有 **GIL（全局解释器锁）**，同一时刻只有一个线程执行字节码，CPU 密集场景多线程跑不满多核，得上多进程；IO 密集（发 HTTP 请求、等元素出现）则不受影响。Java 没有这个限制，是真并行，这也是 JMeter 这类压测工具用 Java 写的原因之一。

另外严格说，Java 是先编译成字节码再由 JVM 执行（含 JIT 编译），和 C/C++ 那种纯编译型不一样——说“Java 是编译型”能过，但深问要接得住。

### Q15 换成 ECMobile 真实接口（这是加分点）

```
接口一：用户登录
POST http://localhost/ecmobile/?url=/user/login
Content-Type: application/x-www-form-urlencoded
表单字段：json={"name":"ecshop","password":"ecshop"}
响应：data.session 里返回 uid + sid，后续接口都要带上
```
不同情况：账号密码正确 → 返回 uid/sid；密码错误 → status 返回错误码；json 参数缺失或格式错 → 报错；未带 session → 后续接口鉴权失败。

```
接口二：商品搜索
POST http://localhost/ecmobile/?url=/search
表单字段：json={"session":{"uid":"${uid}","sid":"${sid}"},
              "filter":{"keywords":"P806","sort_by":"price_asc"},
              "pagination":{"page":1,"count":10}}
```
不同情况：正常返回商品列表；关键词为空 → 返回全部或报错；分页超界 → 空列表；session 失效 → 鉴权失败；排序字段非法 → 默认排序。

**两套认证机制都讲，是加分项**：

> ECMobile 这套是 `uid + sid` 放在 json 的 session 字段里传递，不是标准 token；RuoYi-Vue 那边是 `POST /login` 拿 JWT，前端存进 cookie（`Admin-Token`），后续请求走 `Authorization: Bearer <token>`。两种我都做过，机制不一样但思路一样——登录后提取凭证，后续请求带上。
> 〔已修订：加 `[需确认]`——RuoYi 侧是否真在接口层做过（而非仅前端/用例），无记录可查；若没做过就改成“RuoYi 那套我了解机制”，不要说“做过”〕

### Q10 多表联查（换成真实表名）

```sql
SELECT o.order_sn, o.order_amount, og.goods_name, og.goods_number
FROM ecs_order_info o
JOIN ecs_order_goods og ON o.order_id = og.order_id
WHERE o.user_id = 1001;
```

RuoYi 侧用 `sys_user` 左连 `sys_dept` 核对用户归属部门，用 LEFT JOIN 是为了让“没分配部门的用户”也出现在结果里。
