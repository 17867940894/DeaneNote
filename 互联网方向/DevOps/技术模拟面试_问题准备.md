# 简历构建与面试应答指南

> **面向对象**：软件测试工程师（1-3 年经验）


## 一、简历构建

### 1.1 简历构建注意事项

| 类别        | 要求                                                              |
| --------- | --------------------------------------------------------------- |
| **技能分级**  | 内容项需标注掌握程度（精通/熟练/掌握/了解），“精通/熟练”放在核心技能上（如 MySQL、UI 自动化、接口自动化）    |
| **项目排序**  | 按时间倒序书写                                                         |
| **项目周期**  | 控制在 4~10 个月，更长的可增加迭代期数说明（如 xxx CRM 系统 1,2,3 期）                  |
| **性能测试**  | 视能力措辞：参与过性能回归测试 / 辅助执行 Jmeter 脚本 / 独立完成性能测试（非理工科或毕业不足半年，建议用前两者） |
| **自动化框架** | 视能力措辞：使用框架完成自动化测试 / 知晓框架组成 / 辅助过框架搭建                            |
| **电商项目**  | 至少包含买家端（Web/App）和卖家管理平台（管理商品、订单、客户）两块                           |

### 1.2 AI 优化简历

**AI 提示词模板**：

```text
我是一名工作 1 年的测试人员（含半年的大四实习），在应聘软件或互联网方向企业，附件是我拟的个人简历，请对其进行优化，需要让我的简历，对于软件/互联网企业的面试官有着技术人员的专业和吸引力。

要求如下：
1、检查教育背景、成就荣誉、专业技能、工作/项目经历的前后摆放顺序是否合适；如果教育背景或选修的专业不太好（例如：含有职业院校或技术学院等字样，非理工类专业等），则将该章节内容放到最后面。

2、专业技能、工作/项目经历两部分的内容（例如掌握的技能，承担的任务，使用的工具）
   2.1、需要能够前后呼应
   2.2、可以进行适当地拓展，要像有着 2~3 年软件或是互联网测试工作经验的工程师
   2.3、阐述的语言要平实、专业有逻辑，像一个技术人员（非管理人员），要避免使用学生化或是销售化模糊表述，例如"深度参与业务需求评审"中的"深度"，"精准拆解业务逻辑"中的"精准"等

3、避免使用诸如"基本的、基础的，简单的"等弱化性形容词，可以换成诸如"常用，核心"等更自信的词汇，例如"掌握 MySQL 的基础指令"，可以换成"掌握 MySQL 常用指令"

4、由于我的公司是中小型的乙方公司，有些给甲方定制的项目是设计出来的非实际项目，所以对于每个项目而言
   4.1、项目的时间跨度，控制在 4~10 个月的区间
   4.2、项目的名称要去品牌化，不能是有一定知名度的 web 或是 app（例如蘑菇街 App，有赞 App，万里牛等甲方自研的产品）
   4.3、项目的介绍部分可以保留

5、避免以下几个常见的误区
   5.1、Postman 需要同 Newman 一道写出来，不能只写前者
```

## 二、面试应答技巧

### 2.1 核心原则

**回答面试官问题时，尽可能以简历中的项目为基础，按 TAR 原则举例说明**：

> **T(ask) — A(ction) — R(esult) 原则**

| 要素 | 说明 | 示例 |
|---|---|---|
| **Task（任务）** | 当时的背景和目标 | 参与项目一时，需要重构首页和搜索页功能，其中商品搜索是关键路径之一 |
| **Action（行动）** | 你具体做了什么 | 通过 Selenium + Pytest 完成 5 个自动化冒烟脚本，覆盖搜索栏基本功能，集成到 Jenkins 流水线，每晚定时触发 |
| **Result（结果）** | 取得了什么成果 | 上线前拦截了 3 次因前端组件更新导致的搜索框失效问题 |

### 2.2 应答要点

| 要点 | 说明 |
|---|---|
| **承认局限+补充思考** | 可以承认没接触过 xxx，但要接上“但我知道可以 xxx” |
| **避免弱化词** | 避免使用“掌握基础的/了解简单的”，至少改为“常用的” |
| **逻辑化展开** | 按时间线 / 由总到分 / 由整体到局部 / 先基本流再分支流 / 先有效用例再无效用例 |
| **使用关联词** | 首先……，其次/然后……，接着……，最终…… |
| **面试必录音** | 每次面试务必录音，结束后复盘 |
| **重听改进** | 重听自己的陈述，客观找出问题针对性改进 |

### 2.3 TAR 原则示例

```text
Task（任务）：我在参与简历中的项目一时，当时是要重构首页和搜索页功能，团队需要在每次构建后快速验证核心功能是否正常，其中商品搜索是关键路径之一。

Action（行动）：我通过 Selenium + Pytest 的组合，完成了一组大概 5 个自动化冒烟测试脚本，专门覆盖商品搜索栏的基本功能：包括输入关键词、点击搜索按钮、验证结果页是否加载且包含相关商品。脚本被集成到 Jenkins 流水线中，每天晚上定时自动触发执行。

Result（结果）：该冒烟测试成功在上线前拦截了 3 次因前端组件更新导致的搜索框失效问题，还是蛮有效果和成就感的。
```


## 三、面试题库——P1 核心问题

### 3.1 自我介绍

需准备 **3+ 分钟** 的阐述，包括：

1. **学校/专业**（若不好可跳过，直接从毕业后的第一家公司说起）
2. **大学期间奖项**（如有，必须强调）
3. **任职公司**（一句话说明，包括公司业务）
4. **项目介绍**（每个项目三两句话概述，包括主要业务模块及技术架构）
5. **个人任务与技能**（在这些项目中完成的任务，用到的技术、工具、掌握的技能）
6. **个人性格**（如做事稳妥、学习能力强、领导认可、同事关系融洽等）

### 3.2 项目相关问题

#### 项目描述要点

| 要点 | 说明 |
|---|---|
| **阐述顺序** | 甲方提出需求的背景 → 项目的整体功能模块 → 讲流程 |
| **切忌** | 不要一上来就讲功能，要先讲解需求的背景 |
| **本人负责的模块** | 讲清楚负责哪些模块，难点在哪，怎么测试的 |
| **模块追问准备** | 以库存管理为例，需能回答：管什么？主要操作什么？作用是什么？维护页面叫什么？登记完库存后下一步流程是什么？ |

#### 项目交付与测试流程

**项目首次 1.0 发布**：通常 4~7 个月；迭代周期 1~2 个月发布一次

**测试时长**：约占项目总时长的 30%~50%（开发时长 50%+）

**维护项目**：需有老功能回归 + 自动化

**测试流程**：计划会 → 需求评审 → 开发 → 提测 → 测试 → 验收 → 上线 → 线上冒烟

**自动化时机**：接口自动化在系统测试前期（接口先交付）；UI 自动化在系统测试完成后进行

#### 关键统计数值（面试应答参考）

| 项目状态 | 关键数据 |
|---|---|
| **新项目未上线** | 测试版本数、每轮测试时长、发版间隔、用例数、缺陷数 |
| **项目维护阶段** | 迭代间隔（通常 1~2 个月）、每轮测试时长、变更内容、用例数、缺陷数 |
| **用例数** | 按 50~90 个/月折算 |
| **缺陷数** | 按 20~30 个/月折算（全新项目多，迭代项目少） |

### 3.6 印象深刻的缺陷（至少准备 3 个）

**排查思路**：

```text
1. 数据库数据落库确认
   → 业务操作后，查询数据库数据落库是否正确 → 判断是写入模块还是读取模块的问题

2. Fiddler 抓包确认
   → 前端 UI 操作，同步抓包
   → 若请求参数有错（与界面实际输入不符）→ 前端问题
   → 若请求正确但响应结果有错（与预期不符，节点多了/少了/错了）或数据库落地数据有错 → 后端问题
   → 若响应正确但前端显示错误 → 前端问题
```

#### 缺陷示例 1：列表分页翻页后数据重复或丢失

**场景**：测试商品搜索/内容资讯 APP 信息流时，快速滑动触发下拉加载下一页，偶尔出现与上一页完全相同的商品/文章；或 100 条数据只刷出 98 条，页面响应卡顿。

**分析过程**：

1. 检查服务器负载（Linux `top`），发现后台有批量上下架任务在运行
2. 重新启动任务，通过浏览器 F12 观察请求，确认前端每次触底都正确发起了分页请求，`page_no` 和 `page_size` 参数无误
3. 查看后端响应，HTTP 200，但部分页码返回的 ID 存在重复
4. 使用 Postman 模拟前端直接调用该列表接口，传入相同参数，依然返回重复数据 → **锁定后端问题**
5. 协助开发查看服务器日志（`tail -f`），发现数据库排序查询仅依据更新时间，缺少主键作为二级排序条件，后台任务正好在批量更新数据，导致游标分页失效

#### 缺陷示例 2：状态更新后前端页面不刷新

**场景**：CRM 系统中，将商家“合作状态”从“潜在”修改为“已签约”，保存后提示“操作成功”，但当前页面状态依然显示“潜在”，需按 F5 手动刷新才能看到更新。

**分析过程**：

1. 通过 F12 面板查看，PUT 请求成功发出，后端返回 `{code: 200, msg: "success"}`
2. 去数据库核实，状态字段确实已更新 → **排除后端问题**
3. 检查 Console 无报错 → 最终定位：前端在修改成功后，只做了 Toast 提示，**没有重新拉取数据刷新本地 State** → 前端修复

#### 缺陷示例 3：越权访问漏洞（水平越权）

**场景**：普通采购员 A 可通过篡改请求体中的单据 ID，查看其他部门的机密采购合同及付款明细。

**分析过程**：

1. 确认 UI 层面已隐藏入口 → **初步排除前端视觉问题**
2. 使用 Fiddler 设置断点，拦截 POST 请求，将 `purchase_order_id` 篡改为其他部门的单据 ID，重放请求
3. 服务端返回了敏感数据 → **后端接口缺乏资源归属权鉴权**（未校验当前 `User_ID` 与单据 `Owner_ID` 是否匹配）
4. 定为 P0 级别，推动后端增加越权访问拦截逻辑

#### 缺陷示例 4：防重复点击机制失效导致多笔订单

**场景**：弱网环境下（Fiddler 设置延迟）连续快速点击“提交订单”，系统无“处理中”置灰反馈，同一时间生成两笔相同订单。

**分析过程**：

1. 确认点击后按钮未禁用 → 前端未做防抖处理
2. Fiddler 抓包确认两次点击发送了两个一模一样的 POST 请求 → 前端未拦截
3. 用 Postman 手动并发调用两次下单接口，服务端依然创建了两笔订单 → **后端缺乏幂等性校验**
4. 前后端双重缺陷：要求前端增加按钮置灰防抖，后端增加基于 Token 的幂等性校验

### 3.11 缺陷处理与沟通

| 问题 | 要点 |
|---|---|
| **开发不认可缺陷** | 1. 重新确认需求文档 2. 复现并截图/录屏 3. 与开发沟通讨论 4. 仍无法达成共识则找产品经理确认 |
| **缺陷优先级不认可** | 说明业务影响范围和严重程度，提供依据；无法达成共识则找测试经理/产品裁决 |
| **缺陷无法重现** | 重点关注：操作时间序列、被测对象状态（商品/订单/用户状态）、操作日志和数据库记录中找线索 |
| **PM 要求压缩测试时间** | 毕业 ≤1 年：先通知测试 leader/经理；说明风险，协商优先级，优先保证核心功能 |

### 3.12 其他高频问题

| 问题 | 要点 |
|---|---|
| **开发提交测试延期** | 及时反馈项目风险，调整测试计划，优先测试已提交部分 |
| **上线前发现缺陷** | 评估影响范围，紧急缺陷推动修复，非紧急可记录为遗留问题 |
| **Web 页面空白排查** | F12 查看 Console 报错 → Network 查看请求状态 → 确认后端服务是否正常 |
| **Get vs Post** | Get：参数在 URL，有长度限制，可缓存；Post：参数在 Body，无长度限制，不可缓存 |
| **常见响应码** | 200（成功）、301/302（重定向）、400（请求错误）、401（未授权）、403（禁止）、404（未找到）、500（服务器错误）、502（网关错误）、504（超时） |
| **Fiddler 功能** | 抓包、设置断点、模拟弱网、重放请求、修改请求/响应、Host 映射 |
| **Cookie vs Session** | Cookie 存储在客户端，有大小限制；Session 存储在服务端，更安全；Session 依赖 Cookie 传递 Session ID |

### 3.13 数据库（重点）

| 问题 | 要点 |
|---|---|
| **增删改语句** | `INSERT INTO`、`DELETE FROM`、`UPDATE`（修改数据） vs `ALTER TABLE`（修改表结构） |
| **左外连接 vs 内连接** | 内连接只返回匹配的行；左外连接返回左表所有行，右表无匹配则 NULL |
| **索引用途** | 提高查询效率；复合索引需注意最左前缀原则 |
| **查询涉及的表** | 准备 2~3 个项目中实际查询过的表，说明关联关系和查询目的 |

### 3.14 接口测试（重点）

| 问题 | 要点 |
|---|---|
| **接口测试开展** | 接口功能先交付时启动；说明时间节点、脚本编写时长 |
| **结果验证** | HTTP 状态码 + 响应体校验 + 业务规则验证 + 数据库落库验证 |
| **接口数量** | 电商项目 5~15 个/月；非电商项目 5~7 个/月 |
| **准备 2 个业务接口** | 介绍接口功能、请求方式、Header/Body 参数、响应参数及不同响应情况 |
| **接口用例设计** | 等价类/边界值 + 异常场景 + SQL 注入等 |
| **Postman 断言** | 状态码断言、响应体断言（如 `pm.response.json().code === 200`）、业务结果断言 |
| **传参方式** | Query String、Path Variable、Body（JSON/Form）、Header |
| **上下游接口** | 使用变量提取响应内容：`pm.variables.set("token", pm.response.json().data.token)` |
| **数据驱动** | 使用 CSV/JSON 文件，在 Collection Runner 中执行 |
| **接口自动化回归** | Postman + Newman + Python/ Jenkins 集成 |

## 七、面试题库——性能测试（可选，与简历匹配）

| 问题 | 要点 |
|---|---|
| **哪些接口做性能测试** | 核心业务接口（登录、搜索、下单、支付）、高频调用接口 |
| **QPS vs TPS** | QPS 侧重查询，TPS 侧重完整事务（一笔交易可能包含多次查询） |
| **性能指标** | 响应时间、事务成功率、并发数、吞吐量 |
| **P90 响应时间** | 接口不超过 500ms |
| **事务成功率** | 核心接口 ≥99.5%~99.7%；普通接口 ≥99.0% |
| **CPU 平均消耗** | 不高于 70%~90% |
| **并发数（QPS:TPS）** | 约 10:1 |
| **性能指标来源** | 同产品与开发商讨，非产品独自决定 |
| **JMeter 线程组策略** | 以拐点作为停止增并发的信号 |
| **集合点** | 让多线程在同一时刻并发请求，模拟高并发 |
| **JMeter 元件** | 同步定时器、事务控制器、正则表达式提取器、响应断言、HTTP 请求默认值 |

### 9.1 面试应答要点速查

| 要点 | 说明 |
|---|---|
| **项目介绍顺序** | 背景 → 功能模块 → 流程，不要上来就讲功能 |
| **TAR 原则** | Task（任务）→ Action（行动）→ Result（结果） |
| **缺陷排查思路** | 数据库落库 → Fiddler 抓包（前端请求）→ 后端响应 → 前端显示 |
| **承认局限** | “没接触过 xxx，但我知道可以 xxx” |
| **避免弱化词** | 不用“基本的/基础的/简单的”，用“常用的/核心的” |
| **逻辑化展开** | 时间线、总-分、整体-局部、基本流-分支流、有效-无效 |
| **用衔接词** | 首先…其次/然后…接着…最终… |
| **面试录音** | 每次必录，结束后复盘改进 |
